# Спецификация: Безопасные версионные обновления PyFerro (Safe Evolution Engine)

> **Ключевой постулат:** Клиент — дурак, обновление — зло. Любая операция обязана быть транзакционной, обратимой и защищенной от человеческого фактора. Приложение не имеет права потерять ни одного байта данных или зависнуть в нерабочем состоянии.

---

## 1. Концепция и философия

Обновление схемы базы данных и системного окружения — зона максимального риска. 
В реальном мире:
* Клиенты не читают Release Notes.
* Клиенты забывают делать резервные копии.
* Процесс обновления может быть прерван аварийно (`Ctrl+C`, потеря питания, обрыв сети).
* Пользователи могут обновиться сразу через 3–5 мажорных версий.
* Приложение может запускаться с несколькими параллельными процессами (`granian --workers 4`).

Поэтому архитектура версионных обновлений PyFerro строится по принципу **абсолютной защиты (Zero-Trust Defensive Upgrades)**.

---

## 2. Архитектура состояний системы (State Machine)

При запуске сервера ядро PyFerro сверяет версию установленного пакета (`pyferro.__version__`) и версию схемы в служебной таблице `_ferro_migrations`:

```
                    ┌────────────────────────┐
                    │     Старт сервера      │
                    └───────────┬────────────┘
                                │
               ┌────────────────┴────────────────┐
               ▼                                 ▼
      [Версии совпадают]               [db_ver < app_ver]
               │                                 │
               ▼                                 ▼
         Режим NORMAL                 Режим RECOVERY_REQUIRED
     (Штатная работа сайта)          (Режим безопасного обновления)
                                                 │
                                                 ├── Публичный трафик: 503 Maintenance
                                                 └── Админка /crud: Экран обновления
```

1. **Режим `NORMAL`:** Обычный запуск, все маршруты и WSRPC работают в штатном режиме.
2. **Режим `RECOVERY_REQUIRED`:**
   - Публичные HTTP-запросы получают `503 Service Unavailable` (`Retry-After: 60`).
   - WSRPC бизнес-запросы отклоняются с кодом ошибки `-32050 ("Плановое обслуживание")`.
   - Вход в админку `/crud` по мастер-паролю открывает мастер обновления с GUI.

## 3. Предварительный аудит и современные теневые снимки (Pre-flight & Snapshots)

Перед выполнением хотя бы одной строки кода миграции система запускает процедуру абсолютной защиты:

### 3.1. Нативный физический снимок через `VACUUM INTO` (SQLite)
Вместо небезопасного копирования файлов при работающем WAL-журнале вызывается нативная команда SQLite:
```python
# Создает 100% целостный, дефрагментированный снимок на лету без блокировки читателей
snapshot_path = f".ferro_snapshots/snapshot_{from_ver}_{timestamp}.db"
await session.execute(text(f"VACUUM INTO '{snapshot_path}'"))
```
* **Ротация снимков:** Хранятся только последние 3 снимка (FIFO). Старые удаляются автоматически, исключая переполнение диска.

### 3.2. Защита от переполнения диска
* Перед созданием копии проверяется свободное место на накопителе.
* Если `доступно < размер_базы * 2`, обновление **блокируется** до освобождения места.

### 3.3. Safety-Linter (Проверка скрипта на опасные анти-паттерны)
Встроенный инспектор перед запуском валидирует код новой версии:
* ❌ Запрещено добавлять колонки `NOT NULL` без значения `DEFAULT`.
* ❌ Запрещено удалять колонки без предварительного статуса `deprecated` в предыдущей версии (паттерн **Expand & Contract**).
* ❌ Проверяется наличие обязательных функций `pre_check()`, `upgrade()`, `downgrade()`.

## 4. Контракт версионного Python-скрипта (`pyferro/migrations/v0_5_0.py`)

Каждый файл версии изолирован и реализует паттерн **Expand & Contract**:

```python
"""
Версия: 0.5.0
Заголовок: Оптимизация матрицы прав доступа
"""

VERSION = "0.5.0"
TITLE = "Добавление метаданных и ускорение проверки прав"
CHANGELOG = [
    "Добавлено поле summary в таблицу auth_rpc_permission",
    "Создан составной индекс (role_id, method_name)",
    "Синхронизированы права для встроенных системных методов"
]

async def pre_check(ctx) -> bool:
    """Фаза 1: Разведка (только чтение, проверка готовности окружения)."""
    return await ctx.has_table("auth_rpc_permission")


async def upgrade(ctx):
    """Фаза 2: Применение изменений с трансляцией прогресса в GUI."""
    
    # Шаг 1: Проверка и добавление колонки
    await ctx.report_progress(20, "Проверка таблицы прав...")
    if not await ctx.has_column("auth_rpc_permission", "summary"):
        await ctx.report_progress(40, "Добавление поля summary...")
        await ctx.add_column(
            table="auth_rpc_permission",
            column="summary",
            col_type="VARCHAR(255)",
            nullable=True  # Безопасно для существующих записей
        )

    # Шаг 2: Создание индекса
    await ctx.report_progress(70, "Создание оптимизирующего индекса...")
    await ctx.create_index(
        name="ix_role_method",
        table="auth_rpc_permission",
        columns=["role_id", "method_name"],
        if_not_exists=True
    )

    # Шаг 3: Произвольная логика Python (сиды, нормализация данных)
    await ctx.report_progress(90, "Обновление системных сидов...")
    # Доступен прямой ctx.session для ORM-операций

    await ctx.report_progress(100, "Версия 0.5.0 успешно применена!")


async def downgrade(ctx):
    """Фаза 3: Зеркальный откат назад."""
    await ctx.report_progress(50, "Удаление индекса ix_role_method...")
    await ctx.drop_index("ix_role_method", if_exists=True)
    
    # Удаление колонки
    if await ctx.has_column("auth_rpc_permission", "summary"):
        await ctx.drop_column("auth_rpc_permission", "summary")
```

## 5. Архитектура фонового процесса и GUI (WSRPC Stream)

### 5.1. Независимость от браузера (Decoupled Task Manager)
* Запуск обновления регистрируется в серверном `UpgradeTaskManager`.
* Даже если администратор закрыл браузер, перезагрузил компьютер или пропал интернет — задача на сервере **не прерывается** и штатно доходит до конца (или откатывается при ошибке).
* При повторном открытии `/crud` админка сразу подключается к текущему состоянию задачи.

### 5.2. WSRPC API
1. `system.updates.status`:
   - Возвращает текущее состояние (`NORMAL` / `RECOVERY_REQUIRED` / `IN_PROGRESS`), лог проверок и список готовых к накату версий.
2. `system.updates.apply(stream: true)`:
   - Стримит прогресс `0..100%`, текущий шаг и текст логов на фронтенд Svelte 5 через `session.send_stream_chunk()`.
3. `system.updates.rollback`:
   - Принудительный откат на шаг назад или восстановление из физического снимка.

## 6. Алгоритм аварийного спасения (Instant Disaster Recovery)

Если на любом шаге `upgrade()` происходит исключение (`Exception`), обрыв питания или сигнал прерывания (`SIGINT`):

1. **Мгновенный сброс соединений:**
   - Вызывается `await engine.dispose()` — все активные пулы соединений принудительно обрываются.
2. **Физическая подмена файла:**
   - Рабочий файл `app.db` мгновенно заменяется файлом из `.ferro_snapshots/snapshot_...`.
3. **Холодный перезапуск:**
   - Движок переинициализируется на чистой старой базе.
4. **Результат:**
   - Время восстановления — **менее 1 секунды**.
   - Потери данных — **0 байт**.
   - Админ в GUI видит понятный экран: *«Обновление отклонено из-за ошибки: (...). База возвращена в исходное рабочее состояние. Работа сайта продолжается.»*

## 7. Таблица метаданных (`_ferro_migrations`)

```sql
CREATE TABLE IF NOT EXISTS _ferro_migrations (
    version VARCHAR(32) PRIMARY KEY,      -- '0.5.0'
    applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    applied_by VARCHAR(64),               -- 'gui:admin' или 'cli:auto'
    execution_time_ms INTEGER,            -- Время выполнения в миллисекундах
    checksum VARCHAR(64),                 -- SHA-256 файла скрипта для контроля неизменности
    snapshot_path VARCHAR(255)            -- Путь к резервному снимку VACUUM INTO
);
```
