## 1. Introduction & Strategic Focus

PyFerro has already mastered the performance and network transport tiers:
* Ultra-fast Rust-powered RSGI transport (Granian);
* Symmetric full-duplex WSRPC protocol (JSON-RPC 2.0);
* RFC 0002 Tabular Data Compression (40–70% bandwidth reduction);
* Reactive CRUD and Mission Control panel with Row-Level Security (RLS);
* Client SDK `BinaryWSRPC` with reactive `AuthStore`, Web Crypto RSA, and Gatekeeper.

The next strategic leap is **eliminating friction between backend and frontend, abolishing repetitive boilerplate, and delivering gold-standard developer tooling**.

## 2. Track 1: TypeScript Codegen (`pyferro codegen`)

### The Problem
In standard stacks (FastAPI, Django, Express), synchronizing backend schemas with frontend TypeScript types requires bloated OpenAPI JSON specs, third-party parsers, and manual glue code. Renaming a model column or changing RPC parameters frequently leads to runtime bugs.

### PyFerro's Architectural Advantage
All schema metadata is already introspected in-memory:
1. `ModelRegistry.all()` contains SQLAlchemy model metadata (`FieldMeta`): column types, `nullable` flags, primary keys, enums, and foreign keys.
2. `RPC_REGISTRY` contains method signatures, parameter type annotations (`typing.get_type_hints`), `@tabular_response(fields=[...])` decorators, and docstrings.

### CLI Command
```bash
pyferro codegen server:app --out frontend/src/lib/types/ferro.d.ts
```

### Generated Contract (`ferro.d.ts`)
```typescript
/** Auto-generated by PyFerro Codegen. Do not edit manually. */

// 1. Database Model Interfaces
export interface User {
    id: number;
    username: string;
    email: string | null;
    role: 'admin' | 'moderator' | 'user';
    is_active: boolean;
    created_at: string;
}

export interface ForumTopic {
    id: number;
    title: string;
    content: string;
    author_id: number;
    views_count: number;
}

// 2. RPC Call Registry
export interface RpcSchema {
    'forum.get_topic': {
        params: { id: number };
        response: ForumTopic;
    };
    'tasks.list': {
        params?: { limit?: number; offset?: number };
        response: Task[]; // unpacked from @tabular_response
    };
    'admin.cleanup': {
        params?: void;
        response: { status: string; deleted_count: number };
    };
}
```

### Client Integration in `BinaryWSRPC`
```typescript
import { BinaryWSRPC } from './wsrpc';
import type { RpcSchema } from './types/ferro';

export const rpc = new BinaryWSRPC<AuthUser, RpcSchema>();

// Full IDE autocomplete: methods, arguments, and return types!
const topic = await rpc.call('forum.get_topic', { id: 10 }); 
// `topic` is strictly typed as ForumTopic, not `any`! Typos in `id` trigger TS compilation errors.
```

## 3. Track 2: Developer CLI Utility (`pyferro cli`)

### The Problem
Developers currently juggle scattered commands: running servers with `granian`, setting passwords via ad-hoc script arguments, and inspecting routes manually in Python code.

### The Solution
Register a canonical CLI entry point in `pyproject.toml`:
```toml
[project.scripts]
pyferro = "pyferro.cli:main"
```

### Core Subcommands:
1. **`pyferro rpc list [app]`**:
   Displays an interactive terminal table of all registered RPC methods:
   - Method name;
   - Access tier (`public`, `auth`, `admin`);
   - CASL permissions;
   - Docstring presence and quality (with ⚠️ warnings for undocumented methods).
2. **`pyferro models list [app]`**:
   Summary table of CRUD models: table name, column count, hidden attributes, `is_internal` status, and RLS policies.
3. **`pyferro admin create [app] --login admin --password secret`**:
   Safely creates or resets a database superuser (DML, PBKDF2-SHA256).
4. **`pyferro codegen [app] -o [path]`**:
   Generates TypeScript contracts.

## 4. Track 3: Declarative Model Lifecycle Hooks (`@crud_hook`)

### The Problem
PyFerro's CRUD handles creation and mutation automatically. However, real-world applications routinely need side effects:
- Deleting uploaded files from disk when a record is deleted;
- Emitting real-time socket events (`broadcast_notification`) on record creation;
- Computing or normalizing columns (e.g. `slug = slugify(title)`);
- Running custom validation rules before commits.

Currently, developers have to discard built-in CRUD methods and write custom RPC handlers from scratch.

### The Solution
Declarative lifecycle hooks declared directly inside the model's `class Crud`:
```python
class Topic(Base):
    __tablename__ = "topics"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200))
    author_id: Mapped[int] = mapped_column(ForeignKey("users.id"))

    class Crud:
        verbose_name = "Forum Topic"

        async def before_create(self, db_session: AsyncSession, current_user: AuthSession):
            """Automatically attach current user ID before persisting."""
            self.author_id = current_user.user_id

        async def after_create(self, db_session: AsyncSession, current_user: AuthSession):
            """Notify active clients in real time."""
            await broadcast_notification("forum.new_topic", {"id": self.id, "title": self.title})

        async def before_delete(self, db_session: AsyncSession, current_user: AuthSession):
            """Cascade cleanup of disk files."""
            await delete_topic_files(self.id)
```

Built-in handlers (`crud_create`, `crud_update_cell`, `crud_delete`) automatically invoke these hooks within the active database transaction.

## 5. Track 4: In-Memory Testing Client (`FerroTestClient`)

### The Problem
Writing integration tests for socket applications currently requires cumbersome session mocks or launching a live network server on random ports, slowing down test suites and complicating CI/CD pipelines.

### The Solution
A lightweight in-memory socket emulator:
```python
import pytest
from pyferro.testing import FerroTestClient
from server import app

@pytest.mark.asyncio
async def test_forum_workflow():
    async with FerroTestClient(app) as client:
        # 1. Public ping
        pong = await client.rpc("system.ping")
        assert pong == {"status": "pong"}

        # 2. Unauthorized access is denied
        with pytest.raises(RPCError) as exc:
            await client.rpc("topics.create", {"title": "Test"})
        assert exc.value.code == -32000

        # 3. Seamless user context switching without network overhead
        client.login_as(user_id=1, username="admin", role="admin")
        res = await client.rpc("topics.create", {"title": "Test"})
        assert res["id"] == 1

        # 4. Verifies tabular unpacking
        topics = await client.rpc("topics.list")
        assert isinstance(topics, list)
```

### Key Advantages:
* Tests the complete execution chain: CASL/RLS checks, kwargs auto-mapping, `@tabular_response`, and `@invalidates`.
* Speed: Over **10,000 requests per second** within a single process.
* Zero external socket or port dependencies.

## 6. Track 5: `@transactional` Decorator with Auto-Rollback on Disconnect

### The Problem
1. Repetitive boilerplate: `async with async_session() as db: try: ... commit() except: rollback()`.
2. When a client abruptly disconnects (closes the browser tab) during a long operation, the open transaction may hold row locks in PostgreSQL/SQLite until the pool timeout expires.

### The Solution
A dedicated `@transactional` (or `@app.transactional`) decorator:
```python
@app.rpc("orders.checkout")
@app.transactional
async def checkout_order(db: AsyncSession, session: JsonRpcSession, cart_id: int):
    # `db` is auto-injected from app's async_sessionmaker.
    # Commits on successful return.
    # Rolls back on any exception.
    ...
```

### Disconnect Guard:
The decorator automatically registers `session.register_on_close(cleanup)`:
* If the socket closes before the function returns, the transaction is **immediately rolled back** (`await db.rollback()`), preventing connection leaks and stale locks in the database.
