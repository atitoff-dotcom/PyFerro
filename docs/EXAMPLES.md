# 📚 Архитектура тестовых приложений и стартеров PyFerro (Starter Apps)

## 1. Философия и цели

Самая частая причина ухода разработчиков от новых веб-фреймворков — **высокий порог входа** и «синдром чистого листа». Абстрактная документация и пустые каркасы заставляют тратить часы на выяснение того, как правильно организовать архитектуру.

**Концепция Starter Apps:**
* **Обучение через живой код:** Пользователь в один клик из админки получает полностью готовое, работающее приложение.
* **Эталонные практики (Best Practices):** Каждый пример демонстрирует идеальную реализацию конкретного аспекта (SEO, вложенные структуры, кэширование, пагинация).
* **Безопасная песочница:** Пример можно пощупать, изменить код под себя или безопасно удалить, не задев рабочий проект.

## 2. Единые стандарты для примеров и стартеров

Для обеспечения чистоты и безопасности системы установлены жесткие правила:

### 2.1. Изоляция базы данных: префикс `tst_*`
Все таблицы тестовых приложений **обязаны** использовать префикс `tst_`:
* Например: `tst_topics`, `tst_messages`, `tst_meta`.
* **Зачем:**
  1. **Визуальная изоляция:** В админке и СУБД сразу видно, какие таблицы принадлежат примеру, а какие — ядру или бизнес-логике пользователя.
  2. **Защита от конфликтов:** Исключен риск перезаписи пользовательских таблиц (например, если в проекте уже есть таблица `topics`).
  3. **Чистое удаление в 1 клик:** Для деинсталляции примера достаточно безопасно выполнить:
     ```sql
     DROP TABLE IF EXISTS tst_messages;
     DROP TABLE IF EXISTS tst_topics;
     DROP TABLE IF EXISTS tst_meta;
     ```

### 2.2. Защита при инсталляции (Conflict Detection)
Перед установкой стартера и созданием таблиц установщик **обязан проверить базу данных** на наличие существующих таблиц:
* Выполняется инспекция структуры БД (`inspect(engine).get_table_names()`).
* Если целевые таблицы (например, `tst_topics` или `tst_messages`) уже существуют в БД:
  * Процесс прерывается с информативной ошибкой `ConflictError: Таблицы стартера (tst_topics, ...) уже существуют в базе данных`.
  * В админке пользователю предлагается либо удалить существующий пример («Деинсталлировать»), либо выполнить установку с явным флагом принудительной очистки/перезаписи (`overwrite=true`).

### 2.3. Политика дистрибуции: исключение из PyPI и версионирование по GitHub Releases
* **Пакет PyFerro в PyPI остаётся чистым и легковесным:** Никакие тестовые приложения, дампы или тяжелые сиды не включаются в `.whl` или `sdist`.
* **GitHub Releases с тегами версий (Strict Tagging):**
  * В репозитории стартера делаются релизные теги/ветки, соответствующие минорным версиям PyFerro: `v2.0`, `v2.1` и т.д.
  * При установке по кнопке из админки фреймворк запрашивает архив строго под свою текущую версию:
    `https://github.com/{repo}/archive/refs/tags/v{major}.{minor}.zip` (с fallback на `main` для dev-версий).
  * Это исключает поломку стартера из-за рассинхронизации версий.

### 2.4. Решение проблемы миграций при обновлении PyFerro
Когда фреймворк PyFerro обновляется (например, с 2.0 на 2.1):
1. **Отслеживание версии в БД (`tst_meta`):**
   * При установке стартера в служебную таблицу `tst_meta` записывается версия:
     ```sql
     CREATE TABLE IF NOT EXISTS tst_meta (
         starter_id VARCHAR PRIMARY KEY,
         installed_version VARCHAR NOT NULL,
         installed_at TIMESTAMP NOT NULL
     );
     ```
2. **Обнаружение устаревшей схемы:**
   * Если текущая версия фреймворка не совпадает с `installed_version`, админка подсвечивает статус: *«Пример требует обновления под PyFerro {current_version}»*.
3. **Обновление в 1 клик (Reinstall / Reset):**
   * Поскольку данные тестовые (демо-сид), обновление выполняется без сложных и ломких миграций: админка пересоздает таблицы `tst_*` под актуальную схему и заливает свежие данные.

### 2.5. Механизм доставки и установки (Download Flow)
* **Без зависимости от Git:** Скачивание выполняется стандартной библиотекой Python по HTTP (zipball репозитория).
* **Процесс установки:**
  1. Запрос из админки по RPC: `Starters.install(starter_id, overwrite=False)`.
  2. Определение совместимого тега релиза GitHub по версии `pyferro.__version__`.
  3. Проверка БД на конфликт существующих таблиц `tst_*`.
  4. Скачивание архива стартера с GitHub.
  5. Распаковка в изолированную директорию (например, `apps/tst_forum_seo/`).
  6. Создание таблиц `tst_*` и запись метаданных в `tst_meta`.
  7. Запуск сидера (наполнение демонстрационными данными).

## 3. Эталонный пример №1: «SEO-Форум с древовидной структурой»

Первое и ключевое тестовое приложение — древовидный форум, призванный показать идеальную реализацию SEO на сложных связанных данных.

### 3.1. Структура базы данных (всего 2 таблицы + метаданные)

```
┌──────────────────────────────────────┐
│             tst_topics               │
├──────────────────────────────────────┤
│ id (PK)                              │
│ parent_id (FK -> tst_topics.id, NULL)│ <── Древовидная иерархия
│ title (VARCHAR)                      │
│ slug (VARCHAR, UNIQUE)               │ <── ЧПУ для URL
│ is_category (BOOLEAN)                │ <── Раздел или ветка с сообщениями
│ seo_title (VARCHAR, NULL)            │ <── Ручной оверрайд SEO
│ seo_description (TEXT, NULL)         │
│ created_at (TIMESTAMP)               │
│ updated_at (TIMESTAMP)               │
└──────────────────┬───────────────────┘
                   │ 1
                   │
                   │ N
┌──────────────────▼───────────────────┐
│            tst_messages              │
├──────────────────────────────────────┤
│ id (PK)                              │
│ topic_id (FK -> tst_topics.id)       │
│ author_name (VARCHAR)                │
│ content (TEXT)                       │
│ created_at (TIMESTAMP)               │
└──────────────────────────────────────┘
```

### 3.2. Начальный набор данных (Seed)
* Около 10 тем с разной глубиной вложенности (Категория $\rightarrow$ Подраздел $\rightarrow$ Топик).
* Живые ветки сообщений с ответами для проверки пагинации и микроразметки.

### 3.3. Реализуемые SEO-возможности
1. **Хлебные крошки (BreadcrumbList):**
   * Рекурсивный подъем от дочернего топика к корню дерева.
   * Формирование валидного JSON-LD блока `BreadcrumbList`.
2. **Форумная микроразметка (DiscussionForumPosting):**
   * Корневое сообщение топика размечается как `DiscussionForumPosting`.
   * Ответы размечаются как `comment` с подсчетом `commentCount`.
3. **OpenGraph & Twitter Cards:**
   * Автоматическая генерация `og:title`, `og:description` (выжимка первого сообщения) и `og:url`.
4. **Пагинация и каноникалы:**
   * Корректная обработка страниц обсуждений (`?page=2`, `?page=3`).
   * Исключение дублей страниц в индексе поисковиков.
5. **Динамический `sitemap.xml`:**
   * Рекурсивный обход дерева разделов.
   * Вычисление `lastmod` темы по дате самого свежего сообщения в `tst_messages`.

## 4. Спецификация каталога манифестов (Catalog Manifest)

Реестр доступных стартеров публикуется в формате JSON на GitHub:

```json
[
  {
    "id": "starter-forum-seo",
    "name": "SEO Tree Forum",
    "description": "Древовидный форум на 2-х таблицах: эталонная микроразметка JSON-LD, BreadcrumbList, DiscussionForumPosting и sitemap.xml",
    "repo": "pyferro/starter-forum-seo",
    "branch": "main",
    "tag_template": "v{major}.{minor}",
    "tables": ["tst_topics", "tst_messages", "tst_meta"],
    "min_pyferro_version": "2.0.0",
    "tags": ["seo", "forum", "tree", "json-ld", "sitemap"]
  }
]
```
